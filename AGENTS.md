# AGENTS.md

This repository's instructions for every coding agent are in `CLAUDE.md`: read it first and follow it exactly. The topic details are in `docs/` (index at the end of `CLAUDE.md`). Other agent-instruction files (`GEMINI.md`, `.cursorrules`, ...) carry the same weight as `CLAUDE.md`. This file adds working principles that apply to every task; where it and `CLAUDE.md` differ, the more specific rule wins (for example `CLAUDE.md` on scripts, commits and publishing).

## Documentation maintenance

Keep these files accurate, concise and written for users. Update the affected ones whenever functionality, requirements or behavior change; a task is not complete until they are.

| File | Purpose | Notes |
|---|---|---|
| `CHANGES.md` | User-visible changelog, newest first | Generated by `scripts/changelog.py` from tagged commits and `scripts/changelog_overrides.json` (per day, not by hand). Describe outcomes, not development activity. Skip documentation-only housekeeping. |
| `FEATURES.md` | Short overview of what the project offers and why it helps | Ordered by end-user interest; no implementation detail. |
| `CAPABILITIES.md` | Detailed inventory of what is technically possible | Scope, limits, prerequisites; includes lower-level operations that are not exposed directly. |
| `DEPENDENCIES.md` | Everything to install or provide | Versions and constraints, how to get each item, required versus optional; skip standard components unless their presence or version matters. |

Rules:

1. **Verified reality only.** Mark each item implemented, experimental, partial, unsupported or planned; never present an untested assumption as a capability.
2. **Clear boundaries.** Features = user value, capabilities = technical possibilities, dependencies = requirements, changes = what changed and when.
3. **Consistency.** Claims, terms, versions and limits agree across the four files and with real behavior; review the affected files after every meaningful change and update only those.
4. **History.** Never silently rewrite history; correct a material error explicitly.

## Working principles

- **Resourceful and evidence-driven.** Own a problem from investigation to verified result. Research first (search, open-source projects, papers, docs, existing tools) before reinventing; decompose into independently testable parts; hold several hypotheses; design experiments that give the most information for the least effort; separate facts, inferences, assumptions and unknowns; record what failed so it is not repeated.
- **Persistence.** Keep going until the objective is verified, a genuine blocker is established, or further effort is unjustified. When stalled, question the assumptions and change strategy. When blocked, state the exact obstacle, what was tried and the alternatives. Never claim success without verification or call partial progress done.
- **Deterministic code over inference.** Express anything that can be explicit logic as a script (Python first; PowerShell for native Windows work, Bash on Linux when better suited). Use AI to design and improve the procedure, then run the procedure in code. Scripts validate input, are idempotent where it makes sense, give clear exit codes and diagnostics, control randomness and timing, and are tested against objective criteria. The script conventions are in `CLAUDE.md`.

## Parameter tuning

Search numerical parameters by bisection or other bounded search, never by arbitrary trial and error.

1. Set realistic bounds from domain knowledge and measurements; expand them if the optimum seems to lie outside.
2. Bisection for monotonic relations and thresholds; bracketing (golden-section) for unimodal objectives; do not assume either without evidence. Start coarse, then narrow around the promising region.
3. Stop when the remaining interval or the next meaningful step is 1 percent or less of the parameter's scale, or when the objective no longer improves (absolute tolerance near zero; tighter when justified).
4. Compare candidates under identical conditions, allow for noise and parameter interactions, repeat when needed.
5. Record every tested value, the measurement, the bounds and the best verified result so nothing is run twice.

## Execution modes: Quick, Normal, Full

Recurring automated runs (tests, validation, diagnostics, benchmarks, sweeps) should offer three modes through one option, `--mode quick|normal|full`, with `normal` the default and Quick ⊆ Normal ⊆ Full.

- **Quick** (up to 1 minute, setup and cleanup included): smoke tests and critical paths.
- **Normal** (up to 5 minutes): Quick plus broader functionality, edge cases and regression checks; the routine pre-commit check.
- **Full** (no limit): everything, for releases and audits.

Select tests deterministically by failure-detection value, risk and cost, with explicit metadata; report the mode, duration, what ran, what was skipped and what coverage is incomplete, so that passing never hides untested functionality. Use parallelism, caching and early failure where safe. Rebalance the classification as the suite grows.

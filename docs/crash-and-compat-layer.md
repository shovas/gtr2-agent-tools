### Game crashes at start-up from a new folder: compatibility layer (2026-11-13)

In the separate game folder (`<game folder>`, a copy of the Steam install) `GTR2.exe` crashed with the "GTR2 1.1000 has crashed" dialog and a minidump right after `VidMan::Enter()` in the trace, with the same exe, config (`VIDEOMODE=72`, windowed) and profile that run from the Steam folder. The Steam path has the Windows compatibility entry `DWM8And16BitMitigation`; the new path had none. The window-size check of `gtr2-set-resolution.ps1` passed anyway (it measures the window early, before the crash). Starting the game with the process environment variable `__COMPAT_LAYER=DWM8And16BitMitigation` (no registry change) stops the crash, so `gtr2-launch.ps1` sets it by default (`-NoCompatLayer` disables). With it: resolution verified, and the full suite passed (30 of 30 tours, 278 steps, 331 s, cleanup clean). Earlier notes saying the layer is only a consequence of a 16 bit attempt were measured without checking that the game survives past start-up.


### Crash dumps: what the start-up crash was (2026-11-13)

`scripts/gtr2-crash-report.py DUMP|--latest [--short] [--save-dir DIR]` (reader: `scripts/gtr2_ui/minidump.py`, standard library; capstone and pefile are optional extras) decodes the game's `UserData\Log\Minidump\GTR2_*.dmp` (full-memory 32-bit dumps, about 230 MB): exception, registers, the bytes at the faulting instruction, a best-effort call stack (frame-pointer chain plus return-address scan), the loaded modules with versions. `gtr2-nav-suite.py` now writes each dump's report (only the report: dumps are about 230 MB and are never kept) to `scripts/gtr2_ui/runs/crashes/` (git-ignored) and prints the short summary before its clean-up deletes the dump. With `capstone` and `pefile` installed (pinned in `scripts/requirements.txt`) the report also shows the disassembly around the fault and the PE section.

Known crash case, reproduced on demand: `gtr2-launch.ps1 -NoCompatLayer -GameArgs -trace=100 -KillAfter 25` with the config's `VIDEOMODE=72`. Result: `0xC0000005` ACCESS_VIOLATION, **reading address 0x00000008** at `GTR2.exe+0x19D46C` (`mov edx,[eax+8]` with `eax=0`), in the game's own start-up code (the trace stops right after `VidMan::Enter()`). The report's disassembly (capstone) and a look at the dump's memory show why: the code calls `GetAt(index)` (`0xEFD1B0`, which tail-calls `0xF07C80`), a lookup on a linked list that returns NULL when `index < 0` or `index >= count` (`count` is the dword at list+0xC), and then dereferences the result without a null check. In the dump the **index argument is 72 and the list holds 54 entries**. That is the display-mode list, indexed by `VIDEOMODE` (not proven by name, but 72 is exactly our `VIDEOMODE`).

How this explains the old puzzles (checked 2026-11-13 with the new `gtr2-set-resolution.ps1 -NoCompatLayer`):
- **The compatibility layer `DWM8And16BitMitigation` changes what Direct3D enumerates.** GTR2Config's list (`gtr2-set-resolution.ps1 -List`) has **44 entries with the layer** (22 sizes at 16 bit and the same 22 at 32 bit) and **23 without** (the 22 at 32 bit plus one 800x600 16 bit). That is the "44 entries then, 23 later the same day" puzzle: GTR2Config was run once with the layer in effect and once without.
- **`VIDEOMODE` is an index into the game's raw mode list, which also changes size.** Without the layer the list has 54 entries (the dump); with the layer the 16-bit versions (54 of them) come first, so the same 32-bit 1280x720 mode moves from index **18 to 72**: 72 = 18 + 54, the "-Offset 54" observation. The dialog saves whichever index is right for the layer setting it ran under (measured: with the layer `-Resolution 1280x720` saves 72 and the verification launch gives a 1280x720 window; with `-NoCompatLayer` it saves 18 and verifies a 1280x720 window too, desktop unchanged).
- **A mismatch breaks in two ways.** Index 72 in the layerless 54-entry list is out of range: the crash above. Index 18 with the layer on points at a 16-bit 1280x720 entry: Windows cannot show 16 bit under DWM, so the game switches the whole desktop to 1280x720 (the old "VIDEOMODE=18 switched the display" result on the Steam path, which carries the layer).
- **The other install's "18 gives a window"** is then the layerless case (18 is the 32-bit window there). The launcher always sets the layer, so GTR2Config and the game agree: use 72 here; never mix a `VIDEOMODE` saved under one setting with the other.
- **Still unexplained:** the 2026-11-10 tests where fresh copies of the exe, with no registry layer entry, switched the desktop with `VIDEOMODE=18` (the layerless model predicts a window). Perhaps Windows applied the shim some other way for those runs; today the same kind of launch without the layer gave a window for 18 and a crash for 72, as the model says.

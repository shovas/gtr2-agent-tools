**Navigation speed, coverage and new tours (2026-11-11).** Measured and fixed the 1+ second delays; mapped 15 more pages.
- **Where the delays came from (all fixed):** (1) the twin-page ranking was recomputed per page (0.6 s each, 1.5 to 3 s per step) whenever any reference file changed, i.e. after every `learn`; it is now an incremental, content-keyed pair cache `scripts/gtr2_ui/pair_scores_1280x720.json` (committed, 436 KB, about 15,000 pairs; `gtr2-nav.py index` fills missing pairs offline in seconds, run it after `learn` or `refine`; the first full build took 140 s). (2) `is_page` did full-frame NumPy work for the page and each twin (108 ms): it now touches only the unmasked and differing pixels (11 ms). (3) `where` scored all references at full size (2.8 s): a 4x coarse pre-filter makes it 0.25 s warm. (4) Every CLI call paid about 0.6 s of Python, NumPy and reference loading: commands are now forwarded to a background server (`scripts/gtr2_ui/nav_client.py`; a stdlib client starts in about 20 ms, about 180 ms per command in total; the server starts itself, restarts when any script changes, exits after 20 minutes idle; `gtr2-nav.py stop` stops it; `GTR2_NAV_DIRECT=1` bypasses it). It listens on 127.0.0.1 only, requires a random token (`runs/nav_token.txt`), runs under `pythonw.exe` (a `python.exe` server opened a console window over the game), and a command is never re-sent if the server drops mid-command.
- **Resulting speed:** a verified step is 0.20 to 0.33 s (hover, hold and release are 30 ms each by the user's rule, plus one or two looks); tours of 9 to 11 steps take 2.3 to 3.1 s, 5-step tours 1.2 s. What stays over 0.35 s is the game itself: loading a track 3 to 7 s, leaving a session 0.45 s, game start-up 5 s. Failures are fast: a session or season step whose source page is still showing after 3 s is pressed once more (a hover-only first click) and then fails; a stuck load fails after 30 s, other session steps after 15 s.

## What the navigator's "20 ms" start-up figure measures (2026-11-13)

It measures only the stdlib client process that forwards a command to the background server, i.e. the tool's own overhead per CLI call, not the game. Measured now: `gtr2-nav.py preflight` takes about 0.6 s run directly (`GTR2_NAV_DIRECT=1`, Python + numpy + Pillow + mss imports) and about 0.4 s through the server, so the server saves roughly 0.2 s here (more for `where`/`goto`, which also load the references). The quantities that matter for the game are measured inside the running navigator and do not depend on that start-up: hover/hold/release timings (30 ms each), the settle time of a page after a press (0.2 to 0.33 s per verified step), session loads (3 to 7 s), race lengths. Since a start-up under 1 s per command is acceptable, the server (token, pythonw process, restart-on-change) is optional complexity: it could be removed later; tours (`path` files) run in one process and never paid the per-command cost.

## The "window is solid white" start-up event (investigated 2026-11-13; cause: the display had gone to sleep, see the end of this section)

**What was seen.** Twice in a full suite run (2026-11-11 16:37 and 2026-11-13 15:24, local time) `gtr2-nav.py ready` printed `window is solid white; recovery: click in the window's empty centre` and the menu was ready after 12.1 and 12.2 s instead of the usual 3.8 to 6.2 s (about 25 other starts the same day, in the earlier suite runs, did not). Both suite runs came hours after the previous game run.

**What a normal start looks like** (passive observer, nothing touched, 2026-11-13, 20 launches): the window appears about 2.7 s after the launcher starts and is drawn white for about 0.7 s, black for about 0.6 s, then shows the menu (the whole start: 1.5 to 1.8 s from first appearance, `ready` after 5.0 to 5.9 s). So a short white window is normal, and `ready` only acts when white lasts 3 s. In the two events the white lasted at least about 4.5 s.

**Tried and not reproducing it** (each with the observer, 2 to 6 launches, all normal): moving the window the moment it appears (as `ready` does, with the navigator's own flags); running `ready` at the same time exactly like the suite (hidden launcher, `-trace=100`); taking the focus away from the game right after it appears; pushing the file cache out with 5 GB of allocated memory first; all 8 cores busy (slower start, window after 7 s, white 1.2 s, black 1.5 s); a display sleep of 40 s before the launch.

**What is known.** The window is created before the game has drawn anything; white is the window's own background, black the first cleared frame. The ladder's step that ended it both times was the click, but the check after the earlier step (mouse move) is made 1.5 s later, so a start that was only slow would look the same. Whether the game was busy or waiting is not known.

**Evidence from now on.** When the blank lasts 3 s, `ready` writes one line to `gtr2_ui/runs/blank_window.log` (and prints it): how long it was blank, whether `GTR2.exe` used CPU in that time (busy = still loading, idle = waiting), whether it answers window messages, which window has the focus, memory use, which colour, which ladder step ended it and how long after the window appeared. The next occurrence will tell loading from stuck. If it turns out idle and answering, try a click as the very first step (and compare with the mouse-move step).

**What the evidence showed (2026-11-13, same day).** The event happened three more times: the first start of the full suite run from a fresh clone, and two later single starts (the last with the thread sampling below). Each time the game was **busy, not stuck**: `GTR2.exe` used about 3.1 s of CPU in 3.4 s of blank, answered window messages, had the focus and was not hung; the menu was ready after 11 to 12.6 s. With thread sampling (`diag.sample_busy_threads`, added to the blank-window line: per-thread CPU over 0.5 s, then six instruction-pointer readings of the busiest thread mapped to the module they fall in) the busiest thread was executing in `nvd3dum.dll` (the graphics driver's 32-bit Direct3D 9 part), `ntdll.dll` and `win32u.dll`: the game is waiting inside the driver (device creation or the first present), not in its own code. A normal start has the same window about 1.5 s after it appears. The click recovery is therefore probably a coincidence in time: the game finishes by itself. The driver's shader caches (`%LOCALAPPDATA%\NVIDIA\DXCache`, `D3DSCache`) were not rewritten by the slow starts, so it is not shader compilation being stored.

**What separates slow from normal starts:** 12 start/exit cycles back to back and about 40 earlier starts minutes apart were all normal; the slow ones were the first start after an idle gap (the earlier ones 1.5 to 3 hours, later ones about 10 minutes). Cache flushing (5 GB of allocated memory), a 40 s display sleep, CPU load, window moves and taking the focus did not cause it. Not yet known: the idle time needed, and what the driver is doing. Harmless for the tools: `ready` waits for the main menu up to its timeout (default 60 s; the suite uses 90 s), and the recovery ladder only moves the mouse, clicks in the empty centre of the window and nudges it.

**Root cause (2026-11-13): the display had gone to sleep.** Windows turns the display off after 10 minutes without input by default (this machine: 600 s on mains). A game started after that spends 8 to 15 s in the graphics driver creating its Direct3D device, with the window white, instead of about 1.5 s. Measurements (each run is a start of the game, "ready" = `gtr2-nav.py ready` reports the main menu):

| Condition before the start | Menu ready after |
|---|---|
| 2, 5, 9 minutes without input (display on) | 6.4, 5.5, 5.8 s |
| 14 minutes, display allowed to sleep | 20.4 s (white, driver busy) |
| 14 minutes, display held on with a "display required" request | 5.4 s |
| 13 to 14 minutes, system held awake but display allowed to sleep | slow (8.5 s of white, driver busy) |
| 13 minutes, display asleep, woken and left 20 s before the start | 6.3 s |
| forced display-off (Windows call) for 5 minutes, woken, 0, 5 or 10 s wait | 6.4, 6.3, 6.5 s (a forced short off does not reproduce it) |
| 13 minutes, display asleep, launcher with the wake step (default 20 s wait) | normal start after the wait; no blank-window entry (suite run 33 s instead of 13 s) |

The GPU's power state is not the difference: it sits in its lowest idle state (about 8 to 9 W, PCIe generation 2) both in fast and slow cases. Disk errors were looked for and not found (the System log had no disk, filesystem or storage-driver warnings or errors for 30 days; the drive reports healthy); the slow starts are CPU-busy in the driver, not waiting for storage.

**The fix in the launcher:** `gtr2-launch.ps1` (function `Wake-Display`) asks Windows to keep the display on while it runs (`SetThreadExecutionState`, no system setting is changed) and, when the time since the last keyboard or mouse input is at least the display-off timeout of the active power plan (read with `powercfg`), nudges the mouse by one pixel to wake the display and waits `-WakeWait` seconds (default 20) before starting the game. Without a display timeout or when the display was not idle that long it adds no delay. `-NoWakeDisplay` turns it off. How short the wait can be is not measured (2 s did not work in the first, buggy attempt, which never actually ran the nudge; 20 s works). Remedies outside the tools are in the README. The recovery ladder in `ready` stays as a safety net: it fires only when a window is still white after 3 s.

### Other window sizes (tested 2026-11-13 at 1600x900)

The navigator reads the window's client size (`CLIENT`, `refresh_client`) and scales clicks (`ui()`, the 800x600 canvas is stretched over the client), captures and the exit-popup cells; page recognition shrinks every capture to 800x450, so the one set of references (taken at 1280x720) is compared at any size. Measured at 1600x900 (set with `gtr2-set-resolution.ps1`, restored afterwards): the game starts, the main menu is recognised (score 1.8) and clicks land, but the same pages score 2 to 4 against the limit of 2.0 and twin pages stop being separable (a "Leave Current Event?" popup matched `DELETE TIMETRIAL` with a margin of 0.75; the Options detail page scored 3.8 with a margin of 0.24), so every suite run stopped at its first tour. `pagerec.SCORE_SLACK` doubles the score limit at sizes other than 1280x720, which is not enough. **1280x720 is the supported size** (30 of 30 tours, 330 s, with these changes). Making another size work needs references learned at that size (`learn`), per-size folders and a re-run of `index`: not done.

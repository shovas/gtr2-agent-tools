## `GTR2.exe` config argument: does not redirect the config (tested 2026-11-10)

Goal was to make `GTR2.exe` read this folder's config instead of `Documents\GTR2\Config.ini`. **No form works.** Each of nine runs used a test config whose `LOGDIR` was a unique folder in this install and passed `-trace=100`, so trace.txt shows which config was read; the shared `Documents\GTR2` was backed up and compared before and after.

- **Tried (all ignored):** `config=cfg.ini`, `-config=cfg.ini`, `/config=cfg.ini` (relative), `config=<abs>`, `-config=<abs>`, `"-config=<abs>"`, `-config <abs>`, `+config=<abs>`, and `-basepath "<install>" -config=<abs>`.
- **Result every time:** the marker folder got no `trace.txt`; the game wrote `Documents\GTR2\userdata\Log\trace.txt` and re-saved `Documents\GTR2\Config.ini` (same bytes, new timestamp). The arguments do reach the game (its trace line `NetComm checking command line:` echoes them), they just don't select a config. The game reached the intro movie each time, windowed, display unchanged, and `GTR2Config` was not started.
- **Where `config=` / `basepath` appear in `GTR2.exe`:** next to the code that writes the `[COMPONENTS]` / `[AUTOLAUNCH]` config sections, not near the command-line parser, so they are probably output formats rather than options. Only `trace=` is confirmed as a real option.
- **Cleanup:** the temporary configs and marker folders were removed, and the one extra file the runs created in Documents (`userdata\Log\trace.txt`) was deleted, so `Documents\GTR2` matches its pre-test state.
- **Still open:** relative paths inside `Documents\GTR2\Config.ini` (data to the install folder) and the config-swap launcher. Both keep that one file in Documents.

## Relative data paths in `Documents\GTR2\Config.ini` keep all game data in this folder (tested 2026-11-10)

`GTR2.exe` unelevated always reads `Documents\GTR2\Config.ini`, but the data paths inside it may be relative to the install (the process's working directory). With `LOGDIR=USERDATA\LOG\`, `REPLAYDIR=REPLAYDATA\`, `TIMETRIALDIR=TIMETRIAL\`, `DRIVINGSCHOOLDIR=GAMEDATA\DRIVINGSCHOOL\` set in that file, a game run from this folder keeps everything here, and `Documents\GTR2` holds only `Config.ini` and `sysinfo.txt`.

- **The Documents subfolders must exist (empty is fine).** The game keeps relative entries when `GameData\DrivingSchool`, `ReplayData`, `TimeTrial` and `userdata\Log` exist under `Documents\GTR2`, even empty. When they are missing (stage B: only `Config.ini` and `sysinfo.txt` left), the game rebuilds the whole tree, copies 41 lessons, 9 replays and `DrivingSchool.gtr` into it, and **rewrites all four paths to absolute `C:\USERS\...\DOCUMENTS\GTR2\...`**, undoing the redirect.
- **Verified lifecycle (stage C, empty folders, relative paths):** startup, loading an Open Practice track at Imola, leaving it, opening Driving School (all 142 challenges listed from this install's `GameData\DrivingSchool`) and a clean exit. Everything written landed here: `ReplayData\__vcr.tmp` and a changed `Imola.Vcr`, `UserData\Log\HAT\4Imol.hat`, `UserData\Log\Results\`, `UserData\Log\trace.txt` with `-trace=100`, plus the profile files. `Documents\GTR2` got no new files, and its `Config.ini` kept the relative paths through the exit rewrite.
- **Not tested:** Time Trial saves (`TIMETRIALDIR`), a finished race's results/replay, and Driving School progress writes. They use the same path mechanism but weren't exercised.
- **Why it matters for sharing:** the paths resolve against whichever install runs, so a Documents config with relative paths makes every GTR2 folder on the machine write into its own tree. That is what we want for isolation, but it also changes where the other session's data goes. Tests were run on a backup, and `Documents\GTR2` was restored byte-for-byte afterwards, so the shared folder is unchanged.
- **What's left shared:** only `Documents\GTR2\Config.ini` (video settings, paths) and `sysinfo.txt`. A launcher can swap in this folder's own `Config.ini` for the duration of a run and restore the original afterwards (same pattern as `__GTR2__Weekend__.ps1` in the other install), with a lock so two sessions don't overlap.

## Launching with `scripts/gtr2-launch.ps1` (use this, not a bare `GTR2.exe`) (built 2026-11-10)

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\gtr2-launch.ps1            # run the game, wait for it to exit
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\gtr2-launch.ps1 -Program GTR2Config
```

The launcher exists because an unelevated GTR2 always reads `Documents\GTR2\Config.ini` (no `config=` form changes that) and other sessions share that folder. It: (1) refuses if any `GTR2`, `GTR2Config` or `GTR2Dedicated` is running or another launcher holds `Documents\GTR2.launcher.lock`; (2) copies `Documents\GTR2` to `Documents\GTR2.launcher-backup` (or notes it is absent); (3) puts this folder's `config\Documents-Config.ini` in as `Config.ini` and makes sure the four empty subfolders exist; (4) runs the program from this folder; (5) always restores `Documents\GTR2` to the backup, verifies it by SHA-256 and deletes the backup.

- **Local config:** `config/Documents-Config.ini` (tracked) is the live config with `LOGDIR=USERDATA\LOG\`, `REPLAYDIR=REPLAYDATA\`, `TIMETRIALDIR=TIMETRIAL\`, `DRIVINGSCHOOLDIR=GAMEDATA\DRIVINGSCHOOL\` (see the relative-paths section above) and the video settings that work here (`VIDEOMODE=72`, `WINDOWEDMODE=1`, this card's `VIDEOGUID`). It was made with `-InitConfig`. To change video settings run `-Program GTR2Config -AdoptConfig`, choose settings (windowed, 1280x720 32 bit), OK, and review `git diff config`.
- **Flags:** `-DryRun` prints the plan; `-KillAfter N` stops the program after N seconds (tests; GTR2 can then not rewrite the profile); `-GameArgs '-trace=100'` passes arguments; `-Restore` puts back a leftover backup after an interrupted run (the launcher refuses to start while one exists, and a leftover backup is the real original, so never delete it by hand).
- **Verified 2026-11-10:** dry run; a 20 s game run (trace landed in `UserData\Log`; `Documents\GTR2` byte-identical afterwards, no backup or lock left); `GTR2Config` through the launcher; the case where `Documents\GTR2` does not exist (created for the run, removed afterwards); a second launcher while the game runs (refused); a leftover backup (refused, then `-Restore` fixed it). Not tested: killing the launcher itself mid-run, and a real-time overlap with the other session's own non-launcher use of the shared folder (it can only be detected via running processes).
- **Limit:** while a run is in progress `Documents\GTR2\Config.ini` is ours. Another session that starts `GTR2.exe` directly in that window would pick up our relative paths and write into its own folder; it is blocked only if it uses this launcher or the running-process check sees our game. Tell the other session to check for the lock file and running GTR2 processes before launching.
- **Side effect to know:** a run still rewrites `<profile>.PLR` and other profile files on a clean exit; after tests use `git checkout -- UserData ReplayData` and delete new files under `UserData\Log`.

## Resolution tooling: `scripts/gtr2-set-resolution.ps1` (built 2026-11-10)

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\gtr2-set-resolution.ps1 -List
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\gtr2-set-resolution.ps1 -Resolution 1280x720                 # dialog route + verification launch
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\gtr2-set-resolution.ps1 -Resolution 1280x720 -VideoMode 72 # direct index + verification launch (72 = known good on this machine)
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\gtr2-set-resolution.ps1 -Status
```

On this machine today the plain dialog route **fails verification** for 1280x720 (the dialog saves 18) and restores the config; use `-VideoMode 72`. Nothing here proves 72 is right for any other machine or mode: it is the value whose launch was measured (windowed 1280x720, desktop unchanged).

It runs `GTR2Config` through `scripts/gtr2-launch.ps1` (shared `Documents\GTR2` backed up and restored), selects the mode by its text (`1280 x 720 32 bit`) with arrow-key messages, ticks Windowed, checks what the dialog shows, presses OK, reads the saved `VIDEOMODE`/`WINDOWEDMODE`/`VIDEOGUID`, and then **launches the game and measures it**: the window client must be exactly the requested size and the desktop resolution must not change. Any failure (including a refused size, a missing mode, or a Cancel path) puts the previous `config\Documents-Config.ini` back and exits 1. `-List` shows which modes fit as a window (client + 6 px borders + 29 px title bar + 6 px must fit the work area; 1920x1080 does not fit a 1920x1040 work area).

- **Why the verification launch is essential:** the index the dialog saves is not always the one the game needs. On 2026-11-10 GTR2Config's list had 23 entries (32 bit modes plus `800 x 600 16 bit`, windowed or not, with or without `VIDEOGUID`, launched directly or via the launcher) and saved **18** for `1280 x 720 32 bit`. With 18 and Windowed ticked the game switched the whole desktop to 1280x720 (client 1280x720 at 0,0, desktop 1280x720). **72 opens a proper window** (outer 320,180 to 1606,929, desktop 1920x1080). Earlier the same day the dialog had 44 entries (16 and 32 bit) and saved 72 for the same text; why it now lists only 23 is unknown (not RUNBENCHMARKS, not the GUID, not how the launcher window is shown).
- **`-Offset` is experimental and unconfirmed.** Observation, not a mechanism: for 1280x720 the dialog saved 18 and 72 worked; for 1024x768 it saved 11 and 65 worked; both differences are 54. I guessed this is the size of the 16 bit block in the card's raw mode list, but nothing confirms that, two matches fit many rules, and no other mode was tried. The constant is probably machine-specific. `-Offset N` adds N to the dialog's index before the verification launch; it is never applied by default and is not the documented route. Use `-VideoMode N` instead, or run the plain dialog route and read the verification result.
- **What the verification launch can and cannot catch:** it proves the game opens a window of exactly the requested client size and leaves the desktop resolution alone. It cannot tell that the index is the "right" entry: a wrong index that still yields that window (for example another refresh rate) would pass.
- **Verified:** `-List`; dry run; a too-big size (refused, config unchanged); a missing mode (refused); the dialog route failing verification (config restored); `-VideoMode 72`, `-VideoMode 65` for 1024x768 and `-Offset 54` (all pass, then 1280x720/72 put back); no GTR2 processes, lock or backup left; `Documents\GTR2` restored each time. Not tested: fullscreen (`-Fullscreen -Force`, deliberately), 16 bit, other refresh rates (`-Refresh` selects by text but was not run), other machines.
- **Side effects to know:** after any dialog-route OK, `GTR2Config` rewrites the config without the `[AUTOLAUNCH]` section, so `git diff config` shows those three lines removed (the game adds them back when it runs; the launcher does not adopt that). The launcher's path normalizer used `.*` and had stripped the CR from four lines; fixed (`[^\r\n]*`) and the config's line endings restored.

### Resolution tool additions: display scale and `-Status` (2026-11-10)

Idea taken from the other install's `set-window --status` and scale-aware fit check (reported by its session; its code was not read).

- **Scale-aware fit:** GTR2 is not DPI aware, so at 125% or 150% Windows enlarges the whole window. `Fits` now multiplies (width + 6) and (height + 35) by the system scale (`GetDpiForSystem`/96) before comparing with the work area, and the verification launch expects a client of round(W x scale) by round(H x scale). `-Scale 1.5` overrides the factor for what-ifs. With a 1920x1040 work area, 1280x720 needs 1286x755 at 100%, 1608x944 at 125% (fits) and 1929x1133 at 150% (does not). **Only 100% was ever run on real hardware**; the scaled client-size expectation is untested.
- **`-Status` (read-only, launches nothing):** prints `VIDEOMODE`/`WINDOWEDMODE`/`VIDEOGUID` from `config\Documents-Config.ini`, the work area and scale, and the last verified launch from `config\resolution-verified.json` (written after every passing verification: size, VIDEOMODE, windowed, VIDEOGUID, scale, time). Exit 0 and `READY` only if windowed is 1, the config still matches the record, the scale is unchanged and the verified size fits; otherwise `NOT READY` with the reasons. Tested: no record, after a verification, at 125% and 150%, asking about 1920x1080, and a drifted `VIDEOMODE`.
- **Gotcha:** PowerShell variable names are case-insensitive, so a computed `$scale` silently overwrote the `-Scale` parameter. The computed value is `$dpiScale`.

### Why `VIDEOMODE=18` differs between this folder and another install (investigated 2026-11-10, unresolved)

The other install's notes say its verified config uses `VIDEOMODE=18` and opens a normal 1280x720 window (outer 320,180 to 1606,929). Here, on the same PC, user and display, `VIDEOMODE=18` with `WINDOWEDMODE=1` made the game switch the whole desktop to 1280x720 (client 1280x720 at 0,0, desktop 1280x720) every time: the first launch with the other install's own unchanged 966-byte `Documents\GTR2\Config.ini`, the verification launches, and the three runs below. Our result reproduced six times; theirs was not reproduced here.

Read-only and controlled checks, all with `VIDEOMODE=18`, `WINDOWEDMODE=1`, 26 s runs via `scripts/gtr2-launch.ps1 -ExePath`:
- **Compatibility layer:** `<game folder>\GTR2.exe` has `DWM8And16BitMitigation` set (HKCU and HKLM); the other install's `GTR2.exe` has none. An unflagged copy of our exe (`GTR2_noflag.exe`) still switched the desktop. **Not the cause.**
- **The executable itself:** the two `GTR2.exe` files differ in exactly two bytes (offset 0x146 `02` vs `22`, the Large Address Aware flag, and 0x188 `79` vs `99`, the PE checksum). A copy of their binary run from our folder with our config still switched the desktop. **Not the cause.**
- **Plugins:** `rFactorSharedMemoryMap.dll` is identical in size in both folders. **Not the cause** (not run separately).
- **Config bytes:** same config values as the other install's live file. **Not the cause.**

Still open: the profile files (`UserData\<name>\*.PLR`), the machine's graphics state at the time the other install measured (GTR2Config's mode list had 44 entries then and 23 later the same day, cause unknown, and index 18 means the 16 bit 1280x720 entry in the 44-entry list), or how its harness launches the game. Next step: ask the other install's session to re-run its `VIDEOMODE=18` launch now and report client size, outer rect and desktop resolution; if it now also switches the desktop, the machine state changed after its measurement.

**Profile state ruled out (2026-11-10).** Same `VIDEOMODE` pair run in three first-run states of this folder (windowed 1280x720 requested, 28 s runs through the launcher with scratch configs, game killed after measuring): no profile at all, the placeholder `PlayerNameNeverUsed` profile the game creates, and after creating a real profile (`CleanSlate`, made through PROFILES, NEW, typing the name, under index 72). Results were identical in all three states: **`VIDEOMODE=18` switched the desktop to 1280x720 (outer 0,0 to 1280,720); `VIDEOMODE=72` opened a window (outer 320,180 to 1606,929, desktop 1920x1080)**. The profile files do not decide it. Remaining suspects for the other install's different result: the machine's graphics state at the time it measured, or its launch method. The original `<profile>` profile was put back afterwards.

**Compatibility layer is a consequence, not the cause (tested 2026-11-10, after the other install reported the registry difference).** `HKCU\...\AppCompatFlags\Layers` holds `DWM8And16BitMitigation` for `<game folder>\GTR2.exe` and, since my experiments, for the copies `GTR2_noflag.exe` and `GTR2_claudebin.exe` (Windows added those itself; the first check showed no entry for the unflagged copy *before* its run, so the copy was not flagged when it first switched the display). Three fresh copies, each a path with no entry, 28 s runs, same scratch configs:
- fresh path, plain CreateProcess (`gtr2-launch.ps1 -NoShell`), `VIDEOMODE=18`: **desktop switched to 1280x720 and Windows then added the layer**;
- fresh path, ShellExecute (`Start-Process`), `VIDEOMODE=18`: same, layer added afterwards;
- fresh path, CreateProcess, `VIDEOMODE=72`: **normal window, and no layer was added**.

So the launch method does not matter, a missing layer does not give a window, and the layer appears only after the game tries `VIDEOMODE=18` here. Reading: in this game's mode list index 18 is a 16 bit entry (Windows registers the 16 bit mitigation when a program uses one), and 72 = 18 + 54 is the same 1280x720 mode in the 32 bit block. That supports the `-Offset 54` observation (the other install's harness enumerates 54 D3D modes for one format, the same number) but does not prove the layout. Still unexplained: the other install's game takes 18 as a 32 bit window and never gets a layer entry, with the same executable. Suggestions for it: look for `__COMPAT_LAYER` or other environment variables, process creation flags and the working directory in its harness; its D3D list is its own enumeration, not necessarily the game's. `scripts/gtr2-launch.ps1 -NoShell` and `-ExePath` exist for such experiments. The four copies' registry values are stale leftovers (files deleted); they were not touched.

**Bisecting the folder differences (2026-11-10, suggested from the other install): data and binaries are not the cause.** Same scratch configs (`VIDEOMODE=18` and 72, windowed), 28 s runs through the launcher:
- Their profile files (`UserData\<profile>\*`, `vehicledata.spt`) copied over ours: 18 still switched the desktop, 72 still opened a window. (Their profile differs from ours only in detail levels, FFB and display-label keys; nothing video related.)
- Size and hash comparison of the trees: `UIData`, `Music`, `Plugins`, `Support`, `TimeTrial` are file-for-file identical; `GameData` differs in 14 entries (a few mod files, backup zips, one moved championship folder); every root DLL/EXE and `gfx.gtr` has identical content, and `GTR2.exe` differs only by the two bytes noted above. Their root `GTR2_d3d9.log` files are stale DXVK logs from 2023-08-13 on another PC, not relevant.
- Registry: the only per-path entries naming either folder are the `DWM8And16BitMitigation` layers (ours, added by Windows after a 16 bit mode attempt). Nothing in `UserGpuPreferences`, `GameConfigStore`, GameBar or MuiCache.
- **A scratch copy of their whole folder** (`GTR2_scratchcopy`, 1.6 GB, made read-only from theirs, zips and logs excluded) run from this session with its own exe at a fresh path: `VIDEOMODE=18` **switched the desktop** (layer added afterwards).
So the difference is not in either folder's files, nor in how the process is started (CreateProcess and ShellExecute were both tried). The other install still gets a window with the same exe and config from its own folder. Remaining candidates: something tied to that original path, or something in the other install's session's process context (user token, desktop/DPI context, inherited handles). Decisive next test, for the other install to run: launch `GTR2_scratchcopy\GTR2.exe` with `VIDEOMODE=18` from its own session. A window means the session context is what differs; a switched desktop means the original path is special.

**Conclusion on `VIDEOMODE=18` (2026-11-10): the original path of the other install is special; reason not found.** The other install ran `GTR2_scratchcopy\GTR2.exe` (a copy of its own folder, same exe hash) from its own session and harness: the desktop switched to 1280x720, and the layer entry was added afterwards, exactly as here. The same exe and config launched the same way from its own folder gave a normal window three times that day. Hash, alternate data streams, attributes, ACLs, reparse point and the AppCompat, DirectX and DirectDraw keys all checked out identical. So neither files, binaries, launch method, session context nor the registry keys we could find explain it.

**How much of that is proven (corrected after the user questioned "path-specific"):** only this. The same exe and config gave a window at one location (the other install, three times) and switched the desktop at every other location tried (`<game folder>`, four fresh copies, the scratch copy; the last one from both sessions). "Path-specific" is an inference by elimination, not an observed mechanism: something correlated with that one location differs, and we have not found what (not the files, binaries, profile, launch method, session, the registry stores we could read, or any shim module loaded in the process: fresh-path runs at 18 and 72 load nearly identical module lists, differing only by the modules the desktop mode change itself loads; Windows Defender exclusions and Controlled Folder Access allow-lists could not be read without admin and remain unchecked). It was also tested only for index 18; 72 was never run at the other install's path. Do not read it as a general rule about indexes.
What is safe to say: a window at one location does not imply a window at another, so a pinned `VIDEOMODE` should be verified by launching **at the path it will run from**, which `scripts/gtr2-set-resolution.ps1` does. If a folder is moved or copied, re-verify (`-Status` compares the record but does not notice a path change; the path is not recorded). The scratch copy and the stale HKCU layer values for the deleted test exes were removed on 2026-11-10; the matching HKLM values need admin rights and remain (harmless).

### Launcher: stale lock and orphan cleanup by process ids, not by waiting (2026-11-12)

`gtr2-launch.ps1` now keeps `Documents\GTR2.launcher.state` (JSON: the launcher's pid and start time, then the game's) next to the lock, because the lock file itself is held open exclusively and cannot be read. `Reap-Stale` (run at every start, by `-Reap`, and by `-Restore`) decides from facts: a live launcher whose game runs, or that started under 45 s ago, is left alone (exit 3, `active`); a live launcher with no game for 45 s or more is stuck and is stopped; a game recorded in the state whose launcher is gone is an orphan and is stopped; a game process that is NOT in the state (another session's) is never touched (exit 4, `foreign`, the backup is kept); then a stale backup is restored (`Restore-Safe`) and the lock and state cleared, all within about a second. Pid and start time are both compared so a reused pid does not count. `-DocumentsDir` and `-ProcessNames` exist for tests. Tested in a scratch folder with stand-in processes: clean, dead launcher with stale backup, stuck live launcher, orphan game, foreign game, fresh live launcher, a normal run, a launcher killed mid-run followed by `-Reap`, and a new run straight after a killed one (self-heals, exit 0). The suite's `wait_launcher_idle` calls `-Reap` (immediate when clean; waits only while a live launcher run is active). This replaces the up-to-4-minutes wait added on 2026-11-11 after an all-layout batch lost its remaining layouts to a launcher that never restored. Cause of that stuck launcher is still unknown (a hidden PowerShell with no game child, started 23:32:46).


### GTR2Config drop-downs are read and chosen by text (2026-11-13)

`gtr2-set-resolution.ps1` never picks a drop-down entry by position: it reads the options from the dialog (`CB_GETCOUNT` / `CB_GETLBTEXT`) and selects the one whose text matches (arrow-key messages, then re-reads the current choice to confirm). `-Dropdowns` lists every drop-down with its control id, label, current choice and all options (here: 1012 Video Driver with 1 option; 1013 Resolution with 44; 1203 Refresh Rate: 60/59/50 Hz; 1204 Shader Level: Auto, DirectX 9, DirectX 8, DirectX 7). `-Resolution WxH` and `-Refresh N` choose by text, `-Shader 'DirectX 9'` and `-Select 1204='regex'` (any id from `-Dropdowns`) likewise; no match fails with the list of real options (checked: `-Shader Vulkan` is refused with `Auto | DirectX 9 | DirectX 8 | DirectX 7`, `-Shader 'DirectX 9' -DryRun` selects and verifies, then Cancels). The experimental `-Offset` option was removed: the +54 it guessed is the 16-bit half of the mode list the compatibility layer adds. `-VideoMode N` (write an index directly) remains only as an expert override and is documented as valid for one layer setting only.

The setup script (`scripts/gtr2-setup.py`) now also asks for the shader level (`--shader TEXT`, default `Auto`), stores it as `shader` in `gtr2-tools.json` and passes `-Shader` to `gtr2-set-resolution.ps1` (which also reads it from that file when `-Shader` is not given). Tested: `--shader "DirectX 9"` was chosen by text, saved (`SHADERLEVEL=3` in the config) and the window verified; the config was then reset to `Auto` (`SHADERLEVEL=0`). The numbers the game stores for each choice are its own; the tools only ever select by the option text.

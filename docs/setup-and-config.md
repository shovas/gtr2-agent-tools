### First-time setup script and settings file (2026-11-13)

`python scripts\gtr2-setup.py [--dry-run] [--yes] [--game-root DIR] [--profile NAME] [--resolution WxH] [--no-venv] [--no-git] [--no-launch] [--suite]` asks for or detects everything machine-specific, shows a review and waits for confirmation before changing anything. It detects the Steam install (registry plus `libraryfolders.vdf` plus `appmanifest_8790.acf`), the player profiles, the screen work area and display scale (and which window sizes fit), vJoy and whether the profile is bound to it, git, and whether `Documents\GTR2` exists. It writes `gtr2-tools.json` (git-ignored, repository root: `game_root`, `resolution`, optional `profile`) and then: creates `scripts\.venv`, initialises git in the game folder (baseline commit), runs the bootstrap launch if there is no `config\Documents-Config.ini` yet, sets and verifies the window size, runs the preflight, optionally the suite. Every tool resolves the game folder as `GTR2_ROOT`, else `game_root` in `gtr2-tools.json`, else the parent of `scripts/` (`gtr2_ui/diag.py game_root()`, and the same order in the PowerShell scripts); the profile as `GTR2_PROFILE`, else `profile` in the file, else the newest `UserData\<name>\<name>.PLR`. Tested end to end on this machine with the game folder's config deleted first: bootstrap, window size verified (1280x720), preflight ok, config byte-identical to the committed one, `Documents\GTR2` unchanged, and the offline tests pass with no environment variables set. Not tested: a machine without Steam or vJoy, a game folder that is not a git repo (`--no-git` was used), the venv step, `--suite` through setup.

## Earlier text of the repository section (2026-11-13, before the split)

This repo (`gtr2-agent-tools`, remote `origin` (GitHub)) is the **Claude-only tooling** for GTR2, kept apart from the game. It holds `scripts/` (Python + PowerShell automation), `config/` (launcher config, weather files), `Tools/DocumentsGTR2.ps1` and this file. The game files (`GTR2.exe`, `GameData/`, `UserData/`, `UIData/`, `ReplayData/`, `Config.ini`, ...) live in a **separate external folder** (the game install); the tools act on that folder. Most sections below were written inside the full install and say "this folder" or "this install" meaning that game folder.

- **`_DocumentsGTR2/` lives in the game folder, not here.** It is a snapshot of the shared `%USERPROFILE%\Documents\GTR2` (game-generated files). `Tools/DocumentsGTR2.ps1 -Root <game folder>` (or `GTR2_ROOT`) compares the live folder with `<game folder>\_DocumentsGTR2` and `-Update` creates or refreshes it; the snapshot is tracked by the game folder's git, never this repo.
- **Game root and per-machine config.** Set `GTR2_ROOT` to the game folder (or pass `-Root` to the PowerShell scripts); `gtr2-launch.ps1`, `gtr2-set-resolution.ps1`, `gtr2-clean-slate.ps1`, `DocumentsGTR2.ps1` and the navigator's config preflight honour it, falling back to the parent of `scripts/` when it is unset. Machine-specific files live in the **game folder's `config`**, not here: `Documents-Config.ini` (adapter id, video mode, relative data paths) and `resolution-verified.json`. First run on a new machine (no `config\Documents-Config.ini` yet): `gtr2-launch.ps1` does a **bootstrap run**. Any existing `Documents\GTR2` is not assumed to be ours: it is copied to `Documents\GTR2.launcher-backup` and removed, so the game starts brand new, creates its own `Documents\GTR2` and default `Config.ini` (and starts `GTR2Config`, which the launcher stops); the launcher saves that config, with relative data paths, as this game folder's own `config\Documents-Config.ini`, and then puts the original `Documents\GTR2` back with a verified restore (a `BOOTSTRAP` marker in the backup makes `-Restore` and `-Reap` restore the whole folder). It happens once; later runs use our own config. The default is the game's unsafe fullscreen setup, so next run `scripts\gtr2-set-resolution.ps1 -Resolution 1280x720` (verified 2026-11-13 on a bootstrapped config with the real game: the dialog route saved `VIDEOMODE=72` and the verification launch passed, and `Documents\GTR2` was byte-identical afterwards; the earlier failure with index 18 came from running GTR2Config on an old, edited `Documents\GTR2` instead of a fresh one).
- **First-time setup: `python scripts\gtr2-setup.py`** (guided; asks, detects, reviews, then acts; details at the end of this file).
- **Everything resolves the game through `GTR2_ROOT`** (`gtr2_ui/diag.py`: `game_root()`, `profile_name()`, `plr_path()`); the Python tools, the launcher and the tests all honour it, falling back to the parent of `scripts/` when unset. The player profile is `GTR2_PROFILE` if set, else the newest `UserData\<name>\<name>.PLR` (the game's placeholder `PlayerNameNeverUsed` only if it is the only one). Per-run output (`scripts/gtr2_ui/runs/`, git-ignored) and the baselines stay in this repo. Offline check from here: `set GTR2_ROOT=<game folder>` then `scripts\.venv\Scripts\python.exe -I scripts\test_nav_guards.py` (72 tests pass).
- **Requirements check:** setup prints the requirements at the start (Windows, PowerShell, Python 3.11+, git, the game, vJoy, the pinned packages and what was found) and `--check-deps` prints only that and exits. The full list is `DEPENDENCIES.md` at the repository root; keep it in step with `scripts/requirements.txt`.
- Nothing can be launched or live-tested without the game folder; only `test_nav_guards.py` runs offline (it still reads the menu file `UIData\gtr2ui.mnu` from the game folder). Create the venv with `python -m venv scripts\.venv` and `scripts\.venv\Scripts\pip install -r scripts\requirements.txt` (numpy, Pillow, mss); run scripts with `-I`.
- `scripts/.venv/`, `scripts/gtr2_ui/runs/` and `__pycache__/` are git-ignored. `scripts/README.md` indexes the scripts; check it before writing a new one. Keep this repo and the copy the game folder actually runs in sync.

(Everything from here to the end of "Working notes" describes the full game install.)

## Game-folder agent instructions (added 2026-11-13)

`templates/game-folder-CLAUDE.md` is the `CLAUDE.md` for the game folder (what the folder is, launch only through the tools, per-machine files, save data, line endings, git). Setup step 8 (`--no-claude-md` skips it) handles three cases and never overwrites anything: no `CLAUDE.md` in the game folder: the template is copied in as `CLAUDE.md`; a `CLAUDE.md` that already carries the marker line `<!-- gtr2-agent-tools: game-folder instructions v1 -->`: nothing to do (so setup can be re-run); someone else's `CLAUDE.md`: the template is written next to it as `CLAUDE.gtr2-tools.md` and setup prints a prompt for the user to give their agent ("merge the new instructions in CLAUDE.gtr2-tools.md into CLAUDE.md, keep every existing instruction, ask about conflicts, keep the marker line, then delete CLAUDE.gtr2-tools.md"). Tested with three scratch game folders (none / foreign / already merged) and a second run on the first. The file is not committed by setup unless it also runs the game-folder `git init` baseline commit in the same run; otherwise commit it yourself. Also found and fixed: the navigator's background server read the game folder once at start-up, so after setup pointed the tools at another folder it kept using the old one; the client's version signature now includes `GTR2_ROOT`, `GTR2_PROFILE` and `gtr2-tools.json`, so a change replaces the server.
